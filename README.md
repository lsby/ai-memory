# AI Memory

`@lsby/ai-memory` 是一个专为 AI 智能体设计的**类脑长期记忆与自演进库**。

基于嵌入式 **PGlite + pgvector**，它在本地 Node.js 进程内即可完整运行，无需搭建任何外部数据库。它打破了传统智能体“聊完即忘”或“死板拼接上下文”的局限，为智能体构建了一套具备**记忆分层、图谱联想、仿生遗忘与动态技能进化**的完整认知系统。

---

## 为什么需要这样一套记忆系统？

传统的 LLM 智能体通常只有两种记忆模式：

1. **上下文滑动窗口**：聊着聊着前面的内容就被粗暴截断，跨会话直接失忆。
2. **传统外挂 RAG**：收到用户提问后，系统机械地根据向量相似度搜出几条文本，强行拼进 prompt。

这两种方式存在根本缺陷：

- **AI 是被动的**：外部系统塞什么它就看什么，无法像人类一样根据思考过程**自主联想**、顺藤摸瓜去深挖线索。
- **记忆只增不减**：缺乏淘汰机制，历史越多噪音越大，检索质量持续恶化。
- **缺乏抽象与进化**：经历过的事只能当文本存着，无法将反复出现的逻辑抽象沉淀为“新技能”。

`@lsby/ai-memory` 的目标就是模拟人类记忆的工作机制，让智能体真正拥有持久的思考深度与成长性。

### 1. 三级记忆模型（分层与生命周期）

人类的大脑不会把所有信息平铺在意识里。本系统将记忆划分为三个层级：

| 等级         | 角色定位                          | 存储与生命周期特征                                                                                                 |
| :----------- | :-------------------------------- | :----------------------------------------------------------------------------------------------------------------- |
| **零级记忆** | **核心法则 / 人设**               | 智能体的“自我定位”与底层铁律。**永远无条件随每次对话附带**，具有最高优先级，免除遗忘机制。                         |
| **一级记忆** | **工作记忆 (Working Memory)**     | 当前任务正在使用的即时上下文。无条件随对话附带，但容量严格受限；当满载时，系统会自动将低分记忆降级流转到二级记忆。 |
| **二级记忆** | **潜意识网络 (Long-term Memory)** | 智能体长期沉淀的海量经验库。平时隐于后台，系统仅在对话时按需唤起少量相关片段及**发散线索**，受遗忘曲线持续冲刷。   |

### 2. 知识图谱与“回忆延伸”（主动联想机制）

普通向量检索往往只能找到字面语义相似的内容，而找不到“逻辑关联”的内容。本库将记忆构建为一张**知识网络**：

- **双重关联编织**：每当新记忆写入，系统会自动分析其与现有记忆的**关键词重叠度**与**向量相似度**，在节点之间建立带权重的关联边。
- **发散概念词（线索提供）**：在检索时，系统不仅返回匹配的记忆，还会沿着图谱关联边提取出一组**关键词**。
- **主动深挖（回忆延伸）**：系统不会盲目把所有关联内容一股脑塞给 AI，而是把线索交给 AI。AI 可以根据当前的思考自主判断：“这个线索很重要”，然后**主动调用记忆检索工具发起下一轮深挖**。
- **正反馈机制**：被频繁召回和使用的记忆会增加访问频次与保留权重，在遗忘机制中享有更高的存活率——用得越多，记得越牢。

### 3. 仿生遗忘：基于“信息冲刷”，而非物理时间

没有遗忘的记忆系统最终必然死于信息过载。但与传统的“按物理时间过期”不同，本库将记忆衰减改造为**基于信息量冲刷 (Information Displacement) 的衰减模型**：

- **摆脱物理时钟**：人在现实中遗忘某件事，往往不是因为日历翻过了多少页，而是因为“大脑里涌入了太多新事情”。智能体即便休眠一个月，只要期间没有新记忆产生，已有记忆就会完好如初，绝不因挂钟流逝而误删。
- **信息冲刷衰减**：衰减的唯一动力来自**新信息的涌入**。系统使用 `(当前最大序号 - 上次访问序号)` 来衡量“自上次接触该记忆以来，智能体又经历了多少新信息”。
- **抗冲刷保留指数**：由记忆的**初始评分、图谱总关联度、被访问频次**综合决定。与其他记忆编织得越紧密、被调用越频繁的记忆，对新信息冲刷的抵抗力越强（对数级边际递增巩固）。
- **双轨制自然淘汰**：保留指数低于阈值的孤立无用记忆被自动清理；当容量逼近物理上限时，触发末位淘汰。

### 4. 认知进化闭环

系统鼓励智能体像科学家一样思考，而不只是回答问题：

- **猜想与验证**：面对未知问题，AI 可以提出猜想并打上标签（如 `[临时猜想]`），调用工具或执行运算去验证。
- **反思与状态变更**：根据实验结果，AI 可主动更新记忆的标签（如修改为 `[已验证事实]`）、修正关键词或调整置信度。
- **理论抽象与记忆折叠**：当 AI 从多个具体案例中总结出通用规律时，可以提炼一条通用的理论记忆，并主动降低或清理那些冗余的具体案例，实现“认知的精简与升维”。

### 5. 动态工具系统（从“记事”到“学会技能”）

大部分智能体的能力被局限在开发者写好的固定工具列表里。本库允许智能体**在运行中自我编写代码来创造新工具**：

- **运行时生成**：当 AI 发现某种数据格式转换、特定计算逻辑会被反复用到时，它可以自己编写一段纯 JavaScript 代码，将其注册为动态工具。
- **冒烟测试入库**：创建工具时必须附带测试用例，通过自动化运行校验后才会持久化入库。
- **向量自动召回**：后续遇到新问题时，系统会根据用户输入的语义自动匹配并向 AI 提示相关的动态工具，AI 可随时调用。
- **安全沙箱**：所有动态工具均运行在独立的 **QuickJS 隔离沙箱**中，杜绝文件系统、网络访问与外部模块导入，并有严格的超时限制。

### 6. 轻量嵌入式架构

- **零外部服务依赖**：内置基于 WebAssembly 的 **PGlite** 和 **pgvector** 插件，无需本地安装 PostgreSQL 服务，也无需启动 Docker。
- **多模式支持**：支持纯内存模式（用于临时测试、无状态服务）和本地文件持久化模式（自动生成数据目录，开箱即用）。
- **短事务与串行安全**：数据库写操作与图谱更新全部走内部串行调度，模型流式推理和工具调用期间绝不占用长事务，保证性能稳定。

## 场景实例

### 1. 顺藤摸瓜的主动联想（回忆延伸）

传统的向量检索只能单次被动喂养表面文本，而本库的图谱让 AI 具备像人一样“顺着线索自主深挖”的能力。

假设记忆库里此前分散记录了三条经验：

- **记忆 A**：`项目前端统一采用 Vue 3 + TailwindCSS，需适配黑暗模式`（关键词：前端规范）
- **记忆 B**：`所有弹窗与卡片均需适配 dark 模式，主题主色调为 emerald-500`（关键词：暗黑模式、主题色、弹窗）
- **记忆 C**：`所有弹窗内的表单统一使用 Vee-Validate + Zod 做校验，报错在输入框下方标红`（关键词：弹窗、表单校验、Zod）

> 如果是传统检索，面对“帮我写个前端登录组件”，系统通常只能根据提问字面搜出技术栈大纲（记忆 A），根本不会知道暗黑模式的具体主题色是什么，更联想不到深层的表单校验规范。

**而在本库中的实际运行过程：**

1. **初次唤醒**：用户提出需求 _"帮我写一个前端登录组件"_。系统通过初次检索，通过关键词"前端"精准命中了最直接相关的**记忆 A**。
2. **线索发散**：记忆 A 提到了“需适配黑暗模式”，但没有具体细节。系统通过向量匹配查到了相关记忆的关键词，可能就会包含`暗黑模式`，`主题色`等。
3. **深入查找记忆 B**：AI 拿到线索后，主动调用回忆检索工具查询 `暗黑模式 主题色`，精准调出了**记忆 B**——由此获得了暗黑模式的落地细节（`dark:` 样式与 `emerald-500` 主色调）。
4. **二次发散**：在调出记忆 B 的同时，系统顺着记忆 B 的关键词关联，又延伸出了下一层相关的关键词：`弹窗`。
5. **深入查找记忆 C**：AI 再次主动检索 `弹窗`，调出了深层的**记忆 C**（获得了 Vee-Validate + Zod 的规范）。
6. **最终结果**：AI 一步到位给出了既符合 Vue 3 + TailwindCSS、又原生适配暗黑与 emerald-500、还绑好了 Zod 校验规则的完整代码。

整个过程就像人脑联想一样，由 AI 沿着图谱线索**一环扣一环地主动探索**出来，无需人工把所有规范每次都重复复制进 prompt。

### 2. 跨会话记忆与抗遗忘：不靠时钟，靠“信息冲刷”

你在对话中告诉 AI：“以后写 TypeScript 绝对不要用 `any`，所有函数必须标明确切的返回类型”。

- **传统按物理时间遗忘的弊端**：如果按现实天数计算衰减，智能体关机休眠一周，重新打开时记忆就会因为“超时”被误删；而如果短时间内灌入上万条数据，物理时钟才过去一分钟，系统反而来不及遗忘，导致上下文瞬间被撑爆。
- **在本库的“信息冲刷”机制下**：
  1. **休眠不衰减**：智能体即便是闲置一个月没有任何交互（没有新记忆序号产生），这条偏好记忆的保留指数**完全不会衰减**，完好如初。
  2. **经历海量新信息的冲刷**：后来系统接入了处理财务报表的任务，短时间内涌入了 300 条全新的财务与税务知识（产生 300 个新序号）。所有旧记忆都会经历这 300 条新信息的剧烈“冲刷”。
  3. **谁会被遗忘？谁会留下来？**
     - 当时随口聊的一句琐碎闲聊（如“今天天气不错”）：由于**缺乏图谱关联（总关联度低）**，且**从未被再次访问过（访问次数为 0）**，在 300 条新信息的剧烈冲刷下，保留指数迅速跌破阈值，被自然淘汰。
     - 代码风格偏好：它与系统内的代码知识形成关联网络，且拥有较高的重要性评分；即使经历了 300 条无关信息的冲刷，它的保留指数依然远高于淘汰线。
  4. **唤起与正反馈加固**：当用户随后突然说“帮我写个 CSV 解析函数”时，该偏好被重新命中，AI 依然严格输出 0 `any` 的规范代码；而这次命中使它的访问次数再次递增，使它在未来能够抵抗强度更大的新信息冲刷。

### 3. 认知进化：从“记流水账”到“提炼规律”

智能体在日常调用某个第三方接口时，曾在不同日期零散地记下了几条错误记录：

- `"周一 00:02 调用外部结算 API 报错 502"`，标签：`[结算服务, 接口报错]`
- `"周三 00:04 结算 API 再次报错 502"`，标签：`[支付结算, 网关异常]`
- `"周五 00:01 结算 API 依然报 502"`，标签：`[第三方结算, 请求超时]`

在传统基于规则或 SQL 过滤的系统里，因为这几条记录的用词和标签各不相同（AI 在不同时刻入库时，天然不会每次都精准使用一模一样的字面词汇），它们就是三条互不相干的数据孤岛。久而久之，成百上千条无意义的报错流水账会变成严重的检索噪音。

**为什么 AI 能跨越用词差异，敏锐地注意到这些信息？**

- **相似标签的语义聚集**：AI 打的标签虽然字面不完全相同（如“接口报错”与“网关异常”、“结算服务”与“支付结算”），但语义高度相近。
- **联想机制的灵感碰撞**：在后续某次涉及结算问题或系统自我推演时，本库的**联想机制**能够跨越字面差异，**沿着概念网络将这批带有相似标签的记忆同时唤起并展现在 AI 的上下文中**。
- **模式识别（顿悟）**：当这几条原本分散在不同日期的记录被并排摆在 AI 眼前时，AI 像人类一样捕捉到了隐藏的共性——它敏锐地比对了时间戳：_“周一 00:02、周三 00:04、周五 00:01……用词虽然不同，但怎么全集中在零点刚过的那几分钟？”_

**接下来的认知升维过程：**

1. **提出猜想**：AI 推测：_“外部结算服务可能在每日 00:00~00:05 存在例行的定时重启维护”_，并将猜想写为一条新记忆，打上 `[猜想验证中]` 标签。
2. **验证确证与记忆折叠**：在随后的夜间自动任务中证实了这一规律后，AI 意识到底层具体流水账已无保留价值，主动调用记忆工具：
   - 将之前那几条具体的报错流水账**直接删除或降权淘汰**；
   - 抽象提炼出一条全新的高阶通用理论：`[通用理论] 外部结算服务每日 00:00~00:05 进行例行维护，在此窗口期内的调用应自动执行 60 秒退避重试`。
   > _即便 AI 在此过程中没有主动调用删除能力，由于提炼出通用理论后这些具体的报错流水账再也不会被访问，随着系统持续经历新记忆，**信息冲刷**机制也会让它们的保留指数不断衰减，最终被系统自然淘汰。_
3. 记忆库不仅没有随时间膨胀变慢，反而通过“相似标签 + 联想碰撞 -> 提炼高阶规律”，完成了认知的自我净化与升维。

### 4. 动态工具：AI 自己给自己写“新技能”

假设你是一个跨国分布式团队的管理者，经常在会话里让 AI 算跨时区的会议时间（比如东京、伦敦、纽约三地的工作时间交集）。

- **传统纯文本推理**：大模型每次都要在上下文里硬算时差、推导夏令时，一轮耗费上千 token，而且在跨日（+1天/-1天）的心算中经常算错。
- **在本库中，AI 可以自我进化出新能力**：
  1. AI 发现这个计算需求频繁出现且逻辑确定，于是**主动用 JavaScript 编写了一个时区交集计算函数**，并附带了一组测试用例。
  2. 系统在独立的 QuickJS 隔离沙箱中自动运行冒烟测试。测试通过后，该函数被永久保存到智能体的动态工具库中。
  3. 以后只要你再提出类似的时间计算，系统会自动匹配并把这个工具提供给 AI。AI 直接在沙箱内秒级运行，输出 100% 精确的计算结果。

智能体不再仅仅是“记事”，而是能够通过自写代码，不断扩充自己的能力边界。

## 安装与最小示例

```bash
pnpm add @lsby/ai-memory openai zod
```

要求 Node.js 20 及以上。如果要用「外部 PGlite 句柄」模式（见下文「存储」），还需要自己安装 `@electric-sql/pglite` 和 `@electric-sql/pglite-pgvector`。

### 最小示例：让实例自己管理历史

`智能体` 是不带记忆的基础智能体，`带记忆的智能体` 继承它，用法完全一样，只是多了记忆工具和记忆存储。最省事的用法是 `对话`：历史由实例自己保存在内存里。

```ts
import OpenAI from 'openai'
import { z } from 'zod'
import { 智能体 } from '@lsby/ai-memory'

let 客户端 = new OpenAI({ apiKey: process.env['OPENAI_API_KEY'] ?? '' })
let 实例 = new 智能体({ 系统提示词: '你是一个简洁的助手。' })

let 结果 = await 实例.对话({
  命令: '用一句话介绍 TypeScript',
  预期结果Schema: z.object({ 回答: z.string() }),
  预期结果描述: '一句话回答',
  回调: async (): Promise<void> => {},
  openai客户端: 客户端,
  模型名称: 'gpt-4o-mini',
})
console.log(结果.结果?.回答)
```

模型最终通过一个内置的「提交结果」函数，把符合 `预期结果Schema` 的数据交给你，所以返回值永远是带类型的对象，不用自己去解析文本。

### 推荐用法：调用方自己保存历史（`执行回合`）

服务端应用通常要把历史存进数据库、跨进程恢复，这时用 `执行回合`：实例不保存历史，每次把历史传进来，把返回的 `新增上下文` **原样追加**到自己保存的历史末尾即可。

```ts
import { readFile, writeFile } from 'node:fs/promises'
import OpenAI from 'openai'
import { z } from 'zod'
import { 带记忆的智能体, type 智能体消息类型 } from '@lsby/ai-memory'

let 客户端 = new OpenAI({ apiKey: process.env['OPENAI_API_KEY'] ?? '' })
let 回答Schema = z.object({ 回答: z.string() })

let 实例 = new 带记忆的智能体({
  系统提示词: '你是用户的长期助手，需要记住用户的偏好。',
  存储: { 模式: '文件', 路径: './data/memory' },
  向量模型: { 类型: '无' },
  自动截断: { 触发字符数: 200000, 保留字符数: 80000 },
})

let 历史文件 = './data/history.json'

async function 读历史(): Promise<智能体消息类型[]> {
  try {
    return JSON.parse(await readFile(历史文件, 'utf8')) as 智能体消息类型[]
  } catch (_错误) {
    return []
  }
}

async function 存历史(历史: 智能体消息类型[]): Promise<void> {
  await writeFile(历史文件, JSON.stringify(历史))
}

export async function 聊一轮(命令: string): Promise<string | null> {
  let 历史 = await 读历史()
  let 本轮 = await 实例.执行回合({
    命令,
    消息历史: 历史,
    预期结果Schema: 回答Schema,
    预期结果描述: '给用户的回答',
    回调: async (): Promise<void> => {},
    openai客户端: 客户端,
    模型名称: 'gpt-4o-mini',
    当前时间: new Date(),
    追加注入消息: [{ 类型: '用户资料', 内容: '用户昵称：小明；所在城市：上海' }],
  })

  // 1. 前缀变了（改了系统提示词、工具、结果结构，或者是 0.2.x 留下的旧历史）：库没有发请求。
  //    这里的处理是清空历史新开一个对话；你也可以改成「保留旧历史，另存一个新会话」。
  if (本轮.结束原因 === '前缀已变') {
    await 存历史([])
    return await 聊一轮(命令)
  }

  // 2. 触发了自动截断：用 截断后历史 整体替换自己保存的历史，再追加本轮新增的消息。
  //    这是整个库里唯一允许整体替换历史的时机。
  let 基础历史 = 本轮.历史已截断 ? (本轮.截断后历史 ?? 历史) : 历史

  // 3. 其余情况（包括中断、超出最大轮次）：把新增上下文原样追加保存。
  //    首轮的新增上下文里带着那条带指纹的 system 消息，不要丢。
  await 存历史([...基础历史, ...本轮.新增上下文])

  return 本轮.结果?.回答 ?? null
}
```

要点：

- **`新增上下文` 必须原样、按顺序追加**，不要过滤、不要改字段、不要重排。库依赖历史逐字节不变来命中模型商的前缀缓存。
- **首轮的 `新增上下文` 包含 system 消息**，里面带着 `prefixFingerprint`（前缀指纹）。之后每轮库直接用历史里的这条 system，不再重新拼。
- `结束原因` 有 `中断`、`超出最大轮次`、`提取结构化数据失败`、`校验失败次数超出上限`、`前缀已变` 五种。除 `前缀已变` 外，`新增上下文` 里依然是真实发生过的消息，照样追加保存，下一轮才会接得上。
- `前缀已变` 时 **一个请求都没发**，`结果` 为 `null`，`新增上下文` 是空数组，`消息列表` 就是你传进来的历史。
- 用 `对话`（实例保存历史）时，自动截断由实例自己替换历史，不需要你处理；用 `载入对话历史` / `读取对话历史` 可以在重启时恢复和导出。

## 历史只追加、前缀不变

这是库对外的承诺，也是它最重要的设计原则：**发给模型的历史，只往后追加，已有的消息逐字节不变，前缀一旦固定就不再变化。**

### 为什么

主流模型商（OpenAI、方舟、DeepSeek 等）的自动前缀缓存，原理都是比较「这次请求的开头」和「之前请求的开头」是不是逐字节一样：一样的那一段不用重新计算，价格便宜很多、首字也更快。**只要中间有一个字节变了，从那里开始后面全部缓存失效**。所以每轮改一改 system、把当前时间插到开头、悄悄删几条旧消息，都会让缓存形同虚设。

### 五条规范

1. **请求 = 已有历史 + 本轮新增。** 每次请求发出的消息，等于已有历史（逐字节不变）加上本轮新增的消息。库在任何模式下都不改写、不重排、不删除已有的消息。
2. **前缀 = 第一条 system 消息 + 工具定义。** 一个对话里前缀固定；要变，只能新开对话。
3. **每轮会变的内容，一律作为消息追加在本轮末尾。** 包括当前时间、记忆状态、召回结果、你自己的业务资料。
4. **想丢掉前文，只有两条路：新开对话，或者从头截断。** 只有截断时才允许整体替换历史。
5. **支线不影响主历史。** `推演`、`私有反思` 这类不往主历史追加的调用，是从当前历史分出去的支线。`推演` 不检查前缀，也不改动主历史。

### 什么属于前缀

前缀由这些东西决定，库会把它们算成一个 sha256 指纹，存在第一条 system 消息的 `prefixFingerprint` 字段上（发给模型时不会带这个字段）：

- 组装好的系统提示词全文：实例的 `系统提示词` + 工具与格式说明 + `带记忆的智能体` 的记忆提示词；
- 发给模型的工具定义 JSON，包括：实例的 `工具列表`、按次传的 `临时追加工具列表`、被 `记忆工具筛选` 和 `禁用深度推演` 筛过的记忆工具，以及内置的「提交结果」函数——所以 **`预期结果Schema` 和 `预期结果描述` 也算前缀**，一个对话里要用同一份；
- `是否支持函数调用` 的取值（为 `false` 时工具定义不发给模型，指纹里相应也是空）。

每轮发请求前，库按本轮的参数重新算一遍指纹，和历史里 system 上存的比较：一致就照常请求；不一致就 **不发请求**，直接返回 `结束原因: '前缀已变'`。历史里的 system 没有指纹（0.2.x 留下的旧数据），或者历史根本不是以 system 开头，同样按「前缀已变」处理。

> 为什么返回 `结束原因`，而不是抛错？`结束原因` 本来就是库的失败通道（中断、超出最大轮次等），你用同一套逻辑处理即可：新开对话，或者用新前缀重开。

### 什么不属于前缀，该放哪里

下面这些每轮都会变，**不要塞进系统提示词**，而是用对应的按次参数，库会把它们作为消息追加到本轮末尾：

| 内容                                   | 怎么传                           | 说明                                                               |
| :------------------------------------- | :------------------------------- | :----------------------------------------------------------------- |
| 当前时间                               | `当前时间: new Date()`           | 追加一条 `[当前时间: …]`，格式受 `时区` 影响                       |
| 用户资料、业务资料、当前页面状态……     | `追加注入消息: [{ 类型, 内容 }]` | 按 `类型` 去重：同类型最后一条内容没变就不重复追加，变了才追加一条 |
| 记忆状态、召回结果（`带记忆的智能体`） | 库自动追加                       | 零级、一级记忆的最新状态；按需召回的二级记忆。同样按内容去重       |
| 这一轮的问题                           | `命令`                           | 追加在最后                                                         |
| 温度、核采样、最大输出 token 等        | 直接传                           | 不影响消息和工具，不算前缀                                         |

本轮追加顺序固定为：**记忆状态 → 召回结果 → 调用方的注入（按传入顺序）→ 当前时间 → 用户命令**。

```ts
import OpenAI from 'openai'
import { z } from 'zod'
import { 智能体, type 智能体消息类型 } from '@lsby/ai-memory'

let 客户端 = new OpenAI({ apiKey: process.env['OPENAI_API_KEY'] ?? '' })
let 实例 = new 智能体({ 系统提示词: '你是一个客服助手。规则：只回答和订单有关的问题。' }) // 固定规则放这里

let 历史: 智能体消息类型[] = []
for (let 命令 of ['我的订单到哪了？', '能改地址吗？']) {
  let 本轮 = await 实例.执行回合({
    命令,
    消息历史: 历史,
    预期结果Schema: z.object({ 回答: z.string() }),
    预期结果描述: '给用户的回答',
    回调: async (): Promise<void> => {},
    openai客户端: 客户端,
    模型名称: 'gpt-4o-mini',
    当前时间: new Date(), // 每轮变的内容走按次参数
    追加注入消息: [{ 类型: '订单状态', 内容: '订单 1001：已发货，预计明天送达' }],
  })
  历史 = [...历史, ...本轮.新增上下文] // 第二轮的订单状态没变，不会重复追加
}
```

### 手动从头截断

历史太长想丢掉前文时，用导出的 `从头截断`。它返回新数组，不修改传入的历史：

```ts
import { 从头截断, type 智能体消息类型 } from '@lsby/ai-memory'

declare let 历史: 智能体消息类型[]

历史 = 从头截断(历史, { 保留字符数: 60000 })
```

规则：

- 保留第一条 system；
- 只在「真实用户消息」（不是库注入的消息，也不是纠错提示）的边界上切；
- 一轮里的 `tool_calls` 和对应的工具结果不会被拆开，不会出现落单的工具结果；
- 至少保留最后一轮，所以最后一轮本身很长时，结果可能超过 `保留字符数`；
- 切掉以后 **不用手动补** 记忆状态和注入消息：下一轮库在历史里找不到同类型的注入，会按去重规则自动重新追加。

截断后缓存会失效一次（前缀之后的部分变了），所以不要频繁截断，参见下文的「自动截断」。

## 存储

`带记忆的智能体` 的记忆固定存在 PGlite（嵌入式 PostgreSQL）里，三种存储模式：

```ts
import { PGlite } from '@electric-sql/pglite'
import { vector } from '@electric-sql/pglite-pgvector'
import { 带记忆的智能体 } from '@lsby/ai-memory'

// 1. 内存：进程退出就没了，适合测试和无状态服务。这是默认值。
let 内存实例 = new 带记忆的智能体({ 存储: { 模式: '内存' }, 向量模型: { 类型: '无' } })

// 2. 文件：持久化到一个目录，开箱即用。
let 文件实例 = new 带记忆的智能体({
  存储: { 模式: '文件', 路径: './data/memory' },
  向量模型: { 类型: '无' },
})

// 3. 外部句柄：你自己创建和关闭 PGlite（必须带 pgvector 扩展）。
let pglite = new PGlite('./data/shared', { extensions: { vector } })
let 外部实例 = new 带记忆的智能体({
  存储: { 模式: '外部', pglite },
  向量模型: { 类型: '无' },
})

await 内存实例.销毁()
await 文件实例.销毁()
await 外部实例.销毁() // 外部模式：销毁() 不会关闭你的 pglite 句柄
await pglite.close() // 句柄由你自己关
```

- **内存**：实例销毁时关闭自己建的句柄。
- **文件**：同一个进程里同一个路径共用一个句柄（引用计数，最后一个实例销毁时才关闭）。同一路径的打开和关闭在库里是排队进行的：正在关闭的路径，新的打开会等它关完再开，不会出现两个句柄同时占用一个目录。**不同进程不能同时打开同一个目录**，会报「正在被其他进程使用」。
- **外部**：库的 `销毁()` **不会** 关闭这个句柄，谁创建谁关闭。

### 一个 PGlite、每个用户一个 schema

三种模式都可以带 `schema`（不传就是 `public`，和 0.2.x 的数据布局一致，旧的数据目录可以直接打开）。多用户服务可以只持有一个 PGlite 句柄，每个用户一个 schema，数据互不干扰（遗忘用的序号也按 schema 各自独立）：

```ts
import { PGlite } from '@electric-sql/pglite'
import { vector } from '@electric-sql/pglite-pgvector'
import { 删除记忆空间, 带记忆的智能体 } from '@lsby/ai-memory'

let pglite = new PGlite('./data/ai-memory', { extensions: { vector } })

function 创建用户实例(用户id: string): 带记忆的智能体 {
  return new 带记忆的智能体({
    存储: { 模式: '外部', pglite, schema: `u_${用户id}` },
    向量模型: { 类型: '无' },
  })
}

let 小明 = 创建用户实例('xiaoming')
let 小红 = 创建用户实例('xiaohong')
await Promise.all([小明.初始化(), 小红.初始化()])

// 注销用户：先销毁该用户的实例，再删掉他的记忆空间（DROP SCHEMA ... CASCADE）
await 小明.销毁()
await 删除记忆空间(pglite, 'u_xiaoming')
```

- `schema` 名只能是普通标识符（字母、数字、下划线），否则构造时报错。
- `删除记忆空间` 不允许删 `public`，因为 `vector` 扩展装在 `public` 里。
- 删除之前请先销毁用到这个 schema 的实例。

### 连接互斥

PGlite 只有一个连接。kysely 自带的 PGlite 驱动不加锁，事务期间别的请求发来的普通查询会跑进这个事务，两个事务同时开还会互相覆盖。库在内部把驱动包了一层：

- 内存、文件、外部三种模式都走这一层；
- 锁按 PGlite 对象记录，**多个实例共用一个句柄时，排的是同一个队**；
- 普通查询拿一次锁、还一次；事务从 `BEGIN` 一直占到 `COMMIT` 或 `ROLLBACK`；
- 向量（embedding）在事务外先算好，事务里只读缓存，所以一次几百毫秒的 embedding 网络请求不会占着锁，不会拖住共用同一个库的其他用户；
- 带 schema 时，每次拿到连接后先 `SET search_path`，释放时 `RESET search_path`，不会把 search_path 留给你自己在同一个句柄上的查询。

> **警告：不要在事务里触发的回调中，再调用同一个实例（或同一个 PGlite 上任何实例）的读写，否则会死锁。**
>
> 事务持有锁的时候，回调里再去读写数据库，就是自己等自己。会在事务里被调用的回调有：
>
> - `遗忘豁免`（在清理二级记忆的事务里同步调用）；
> - 记忆写入、清理过程中推送的 `回调` 事件，例如 `添加记忆(记忆项, 回调)`、`批量注入记忆(记忆项列表, 回调)`、`更新记忆(id, 选项, 回调)`、`检查并清理二级记忆(回调)` 里收到的 `流程信息` 等事件。
>
> 在这些回调里只做同步计算、记日志、往队列里丢消息；真要读写记忆，等本次调用返回后再做。另外，你直接拿同一个外部句柄做的查询不经过库的锁，可能和库的事务交错，建议只在没有实例运行时才直接操作它。

### 导出连接锁：`在互斥锁内执行`

外部句柄模式下，你可能在同一个 PGlite 上有自己的表（比如共享知识区），想和库的事务排同一个队，避免自己的查询跑进库的事务。库导出了它内部用的那把锁：

```ts
import { 在互斥锁内执行 } from '@lsby/ai-memory'

let 数量 = await 在互斥锁内执行(pglite, async (): Promise<number> => {
  let 结果 = await pglite.query<{ n: number }>('SELECT count(*)::int AS n FROM "shared"."知识表"')
  return 结果.rows[0]?.n ?? 0
})
```

- 签名：`在互斥锁内执行<R>(pglite: PGlite, 操作: () => Promise<R>): Promise<R>`；等待 PGlite 就绪后，按先进先出排队，轮到时执行 `操作`，结束（含抛错）后放锁，返回 `操作` 的结果；
- 和库实例用的是同一把锁（按 PGlite 对象记录）：库的事务进行中，锁内操作要等事务结束；锁内操作执行期间，库的读写也要等；
- **操作里不要再调用同一个 PGlite 上任何库实例的读写（查询记忆、写入、对话等），否则会死锁**；
- 操作里自己的查询请用带 schema 的全限定表名；如果要依赖 `search_path`，请自己 `SET search_path`，并在结束前 `RESET search_path`，不要留给后面的请求。

## 变更记录与彻底删除

每次记忆变更都会记一笔提交和变更明细，用于 `查询记忆提交` 和 `回退最近记忆提交`。它是占空间的大头，所以可以配置：

```ts
import { 带记忆的智能体, 记忆等级 } from '@lsby/ai-memory'

// 默认：无限保留（和 0.2.x 一样）
let 默认 = new 带记忆的智能体({ 向量模型: { 类型: '无' } })

// 只保留最近 5 个提交，旧的自动裁掉
let 保留五个 = new 带记忆的智能体({ 变更记录: { 保留提交数: 5 }, 向量模型: { 类型: '无' } })

// 完全不写变更记录：回退最近记忆提交 不可用（返回 false），查询记忆提交 返回空数组
let 不写变更 = new 带记忆的智能体({ 变更记录: false, 向量模型: { 类型: '无' } })

// 彻底删除记忆：删掉记忆本身，并抹掉变更表里这条记忆相关的所有旧值和新值，之后无法回退找回。
// 用户主动删除、注销时用。原来的 删除记忆 行为不变（变更记录里还留着，可以回退）。
let 记忆 = await 默认.添加记忆({
  内容: '用户的手机号是 138****0000',
  关键词: ['手机号'],
  标签: [],
  评分: 80,
  等级: 记忆等级.二级,
  创建时间: new Date(),
})
await 默认.彻底删除记忆(记忆.id)
```

`保留提交数` 必须是不小于 1 的整数，否则构造时报错。

### 空间回收（VACUUM）

PGlite 里没有后台自动清理。被删掉的行（裁掉的旧提交、彻底删除的内容）只是被标记为「已删除」，既一直占着磁盘，新写入也用不上这些空间。所以：

- 配置了 `保留提交数` 时，库每过 `max(保留提交数, 5)` 次提交，就在事务外自动对记忆相关的四张表执行一次 `VACUUM`；
- `彻底删除记忆` 抹掉了内容后，会立刻回收一次，让残留的原文可以被覆盖；
- 回收失败（比如实例刚好被销毁）不影响已经提交的业务结果；
- 默认的「无限保留」不裁剪任何东西，所以不需要回收。

### 实测空间数据

下面是「一个 PGlite 里 200 个 schema，每个用户 50 条记忆」的实测结果（**PGlite 0.5.5，本机实测**，仅供估算，实际大小随记忆内容长短变化）：

| 配置                                        | 平均每个用户占用 |
| :------------------------------------------ | :--------------- |
| 不用向量                                    | 约 0.6 ~ 0.7 MB  |
| 1024 维向量 + 默认变更记录（无限保留）      | 约 1.4 MB        |
| 1024 维向量 + `变更记录: false`（不写变更） | 约 0.86 MB       |
| 1024 维向量 + `变更记录: { 保留提交数: 5 }` | 约 1.1 MB        |

## 配置项

下面这些都是 `带记忆的智能体`（部分在 `智能体`）构造时的选项，**在实例上设置**。

### 向量模型

`向量模型` 有三种：`{ 类型: '无' }`、`{ 类型: '本地', ... }`、`{ 类型: '在线', openai客户端, 模型名称, 维度? }`。在线模型的默认输出维度可能很大（比如 2000 多），可以用可选的 `维度`（正整数）让服务端按指定维度输出，请求里会带 `dimensions`、少占存储；不传则行为不变。返回的向量长度和 `维度` 不一致时，这次取向量按失败处理，不会静默截断。换 `维度` 后，已存的旧向量长度不同，需要重新生成。

### 记忆工具筛选与工具名常量

`带记忆的智能体` 默认挂 23 个记忆专用工具（添加/修改/删除零、一、二级记忆，回忆延伸，关键词与标签管理，动态工具，执行代码，深度推演）。用 `记忆工具筛选` 决定挂哪些；被筛掉的工具既不挂给模型，也不会出现在默认记忆提示词里。工具名用导出的常量 `记忆工具名`，不用手写字符串（`全部记忆工具名` 是完整列表）：

```ts
import { 记忆工具名, 带记忆的智能体 } from '@lsby/ai-memory'

// 只允许模型「回忆」和「添加二级记忆」，不让它改、删别的记忆
let 只读加追加 = new 带记忆的智能体({
  向量模型: { 类型: '无' },
  记忆工具筛选: (工具名): boolean => 工具名 === 记忆工具名.回忆延伸 || 工具名 === 记忆工具名.添加二级记忆,
})

// 记忆工具全部不挂：比如只想要一个引导对话
let 无记忆工具 = new 带记忆的智能体({ 向量模型: { 类型: '无' }, 记忆工具筛选: (): boolean => false })
```

- 筛选函数在构造时对每个工具名只调用一次，结果在实例生命周期内固定。
- 工具定义是前缀的一部分：换了筛选，用旧历史会得到 `前缀已变`。
- `深度推演` 同时受 `禁用深度推演` 控制，两者任一关闭就不挂。

### 记忆提示词

`带记忆的智能体` 会在系统提示词里拼一段「怎么使用记忆」的说明。默认文本按启用的工具分段拼接（三级记忆、认知进化、关键词与标签、动态工具……），只写和已启用工具相关的段落；全部启用时和 0.2.3 版一字不差。你可以整段替换，也可以基于默认文本修改：

```ts
import { 生成默认记忆提示词, 带记忆的智能体 } from '@lsby/ai-memory'

// 传字符串：整段替换
let 全替换 = new 带记忆的智能体({
  向量模型: { 类型: '无' },
  记忆提示词: '你有长期记忆。需要记住的事用 add_level_2_memory 保存，需要回想时用 extend_memory。',
})

// 传函数：收到启用的工具名列表（构造时只调用一次），返回提示词
let 在默认基础上追加 = new 带记忆的智能体({
  向量模型: { 类型: '无' },
  记忆提示词: (启用的工具名): string => `${生成默认记忆提示词(启用的工具名)}\n\n补充规则：用户的隐私信息不要写入记忆。`,
})
```

记忆提示词是前缀的一部分，只能在实例上设置，换了会让旧历史 `前缀已变`。

### 禁用深度推演

`深度推演` 是一个让模型起子智能体、在记忆上做推演的工具。不需要的话在实例上关掉：

```ts
import { 带记忆的智能体 } from '@lsby/ai-memory'

let 实例 = new 带记忆的智能体({ 向量模型: { 类型: '无' }, 禁用深度推演: true })
```

0.2.x 里这是按次传的参数，0.3.0 起改到实例上（工具列表属于前缀，不能每轮变）。

### 时区

注入的 `[当前时间: …]` 和记忆列表里的「记录于…」默认用服务器时区。可以在实例上设置默认时区，也可以每次调用单独传，按次的优先。时间注入是按次追加的，换时区不影响前缀：

```ts
import OpenAI from 'openai'
import { z } from 'zod'
import { 带记忆的智能体 } from '@lsby/ai-memory'

declare let 客户端: OpenAI

let 实例 = new 带记忆的智能体({ 向量模型: { 类型: '无' }, 时区: 'Asia/Shanghai' })

await 实例.对话({
  命令: '现在几点了？',
  预期结果Schema: z.object({ 回答: z.string() }),
  预期结果描述: '回答',
  回调: async (): Promise<void> => {},
  openai客户端: 客户端,
  模型名称: 'gpt-4o-mini',
  当前时间: new Date(),
  时区: 'America/New_York', // 这一次按纽约时间
})
```

时区必须是有效的 IANA 名称（如 `Asia/Shanghai`、`America/New_York`、`UTC`），否则构造时（或调用时，且不发请求）报错。

### 额外请求参数

各家模型的私有参数（比如豆包的 `thinking`）从这里传，会合并进每次请求的请求体：

```ts
import { 带记忆的智能体 } from '@lsby/ai-memory'

// 以豆包为例：关闭深度思考
let 实例 = new 带记忆的智能体({
  向量模型: { 类型: '无' },
  额外请求参数: { thinking: { type: 'disabled' } },
})
```

- 不能包含库自己管理的字段 `model`、`messages`、`tools`、`stream`、`stream_options`，否则构造时报错。
- 构造时会复制一份，之后再改你传入的对象不影响实例。
- 它不改变消息和工具，所以 **不算进前缀指纹**；一个对话里请自己保证不换参数。

### 遗忘豁免

按默认参数写入大量低分记忆时，自然遗忘和末位淘汰会把它们清掉。用 `遗忘豁免` 保住关键事实：返回 `true` 的二级记忆不参与自然遗忘和末位淘汰。默认不豁免任何记忆。

```ts
import { 带记忆的智能体 } from '@lsby/ai-memory'

let 实例 = new 带记忆的智能体({
  向量模型: { 类型: '无' },
  遗忘豁免: (记忆): boolean => 记忆.标签.includes('关键事实'),
})
```

注意：回调在清理的事务里 **同步** 调用，不要在里面读写记忆或发网络请求（见上文死锁警告）。被豁免的记忆仍然计入 `二级记忆数量上限`。遗忘阈值、衰减常数等参数（`二级记忆遗忘分数阈值`、`二级记忆衰减常数k` 等）不变，可以按需自己调。

### 受保护标签

记忆工具 `edit_level_0_memory`、`edit_level_1_memory` 要求模型传完整的新标签列表，`overwrite_memory_tags`、`remove_memory_tags` 也能删标签。如果你用标签表达业务语义（例如用 `遗忘豁免` 判断某类记忆不遗忘），模型一改标签就丢了。用 `受保护标签` 声明哪些标签模型动不了：

```ts
let 实例 = new 带记忆的智能体({
  向量模型: { 类型: '无' },
  受保护标签: (标签): boolean => 标签 === '遗忘豁免' || 标签.startsWith('来源:'),
  遗忘豁免: (记忆): boolean => 记忆.标签.includes('遗忘豁免'),
})
```

- 对所有**由模型工具发起**的标签变更生效：`edit_level_0_memory`、`edit_level_1_memory`、`overwrite_memory_tags`、`remove_memory_tags`、`append_memory_tags`，以及三个 `add_level_*_memory`（新增记忆时带的标签）；
- 原记忆上命中规则的标签一律保留（即使模型传的新列表里没有）；模型想新增命中规则的标签会被忽略（防止模型伪造 `来源:手动`）；不命中的普通标签照常改；
- 工具返回给模型的 `最新状态` 如实反映最终标签；
- 你自己通过公开方法（`添加记忆`、`更新记忆`、`批量注入记忆`）改标签不受限制；
- 只影响工具的执行结果，不改系统提示词和工具定义，所以不影响前缀；默认提示词里也不提它（需要的话，在自己的 `记忆提示词` 里告诉模型哪些标签不要动）；
- 回调在工具执行的事务里同步调用，不要在里面读写记忆或发网络请求；
- 不传则行为和之前完全一致。

### 自动截断

对话越长越贵越慢，但每轮都截又会让缓存反复失效。`自动截断` 用「回差」解决：历史超过 `触发字符数` 才截，一次截到 `保留字符数`，两个值之间留出很大的空间，一次截断就能撑很多轮：

```ts
import { 智能体 } from '@lsby/ai-memory'

let 实例 = new 智能体({
  自动截断: {
    触发字符数: 200000, // 超过这个数才截
    保留字符数: 80000, // 截到这个数（大约 40%）
    触发token数: 60000, // 可选：拿得到上一次输入 token 数时，优先按它判断
  },
})
```

- 字符数按 Unicode 码点计数（口径同导出的 `统计字符数`），统计的是实际发给模型的序列化消息。
- `触发token数` 要和「上一次请求的输入 token 数」配合才生效。用 `对话` 时实例会自动记录；用 `执行回合` 时由你在下一轮通过 `上次输入token数` 传入（取上一轮 `用量` 里最后一项的 `输入token数`）。没传时按字符数判断。
- 发生了截断，返回结果里 `历史已截断` 为 `true`，`截断后历史` 是截断后的历史。**调用方用它整体替换自己保存的历史，再追加 `新增上下文`**（完整写法见上文「推荐用法」）。用 `对话` 时实例已经替换好了。

### 用量（缓存命中）

每次模型请求都会记录一项真实用量，放在返回结果的 `用量` 数组里。缓存命中数读的是模型商返回的 `usage.prompt_tokens_details.cached_tokens`，读不到的字段留空：

```ts
import OpenAI from 'openai'
import { z } from 'zod'
import { 智能体 } from '@lsby/ai-memory'

declare let 客户端: OpenAI
declare let 实例: 智能体

let 本轮 = await 实例.对话({
  命令: '你好',
  预期结果Schema: z.object({ 回答: z.string() }),
  预期结果描述: '回答',
  回调: async (): Promise<void> => {},
  openai客户端: 客户端,
  模型名称: 'gpt-4o-mini',
})

for (let 项 of 本轮.用量) {
  let 输入 = 项.输入token数 ?? 0
  let 命中 = 项.缓存命中token数 ?? 0
  console.log(`输入 ${String(输入)}，缓存命中 ${String(命中)}，输出 ${String(项.输出token数 ?? 0)}`)
  if (输入 > 0) console.log(`命中率 ${String(Math.round((命中 / 输入) * 100))}%`)
}
```

旧的 `读取模型审计汇总()` 只能按「是不是新建对话」来猜缓存，有了 `用量` 才能核对缓存到底命中了没有。

## 哪些只能在实例上设置，哪些可以按次传

判断标准只有一个：**会不会改变前缀（第一条 system 和工具定义）**。会改变的，只能在实例上设置，一个对话里固定；不改变的，可以每次调用都不一样。

| 位置                 | 选项                                                                                                                                                                       | 说明                                    |
| :------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :-------------------------------------- |
| 实例上（影响前缀）   | `系统提示词`、`工具列表`、`记忆工具筛选`、`记忆提示词`、`禁用深度推演`                                                                                                     | 改了就是 `前缀已变`，要新开对话         |
| 实例上（不影响前缀） | `自动截断`、`额外请求参数`、`时区`（也可按次）、`变更记录`、`遗忘豁免`、`受保护标签`、`存储`、`向量模型`、`一级记忆容量` 等记忆参数、`最大校验重试次数`、`最大循环轮次` 等 | 额外请求参数请自己保证一个对话里不换    |
| 按次传（影响前缀）   | `预期结果Schema`、`预期结果描述`、`临时追加工具列表`、`是否支持函数调用`                                                                                                   | 一个对话里要用同一份；变了会 `前缀已变` |
| 按次传（不影响前缀） | `命令`、`当前时间`、`追加注入消息`、`时区`、`温度`、`核采样`、`最大输出token`、`中断信号`、`结果验证器`、`上次输入token数`、`标题`、`是否自动召回`、`模型名称` 等          |                                         |
